# 2026-09-16 — P3: FIG13 / A2 Gram inversion, H5's re-specified deciding test, run on real data

## What happened

Built `attacks/inversion.py` (the realistic, reference-based adversary; the "oracle" alignment
against ground truth is a correctness self-test only, not a reported curve — see the module
docstring for why an oracle curve would be tautological, always ~1.0, given RESEARCH_PLAN.md §3.4's
own stated fact that the Gram statistic loses no span information, ever). Caught and fixed a real
shape bug in `orthogonal_procrustes` via a direct unit test with a known rotation before trusting it
on anything else (`M = B @ A.T`, not `B.T @ A` — the earlier version produced a `(d,d)` matrix instead
of `(n,n)`, which would have silently corrupted every downstream cosine-similarity number had it not
been caught).

Ran `run_gram_inversion.py` on real cached CUB-200 and CIFAR-100 features (both backbones' primary
`vit_base_patch16_224.augreg_in21k` cache), n_per_class in `{1,2,4,8,16,(32,64,128 where the dataset
has enough per-class samples)}`, 3 reference-quality conditions (clean/full pool, clean/small pool,
noisy/full pool), 5 trials per cell — 195 rows, `results/fig13_gram_inversion.csv` +
`results/fig13_anisotropy.csv`.

## The result

- **n=1 is exact everywhere** (cosine = 1.000), confirming the claim test's algebra holds on real
  features too, not just synthetic ones.
- **Beyond n=1, cosine similarity drops substantially and does not recover** — CIFAR-100 falls to the
  0.4-0.6 range by n=8 and stays there through n=128; CUB-200 similarly falls to ~0.65-0.70 by n=8-16
  (CUB's per-class n rarely exceeds ~25-30, so 32/64/128 mostly have no data to draw from — correctly
  skipped, not zero-filled).
- **CUB-200 retains more than CIFAR-100 at matched n** (e.g. n=16: CUB ~0.65-0.70 vs CIFAR ~0.45-0.53),
  consistent with `02_DATASETS.md`'s prediction that CUB is "the best case" for this attack (small,
  fine-grained per-class n) — a real, data-driven confirmation of a design choice made before any
  data existed.
- **Reference quality (noise, pool size) has a real but noisier effect** than n itself at only 5
  trials/cell — some cells show the "obviously wrong" direction (noisy sometimes beats clean at a
  given n), which is very likely just small-sample variance given the trial count, not a real
  reversal. **This needs more trials before the reference-quality axis specifically is trusted** —
  the n-dependence is the robust part of this result, the reference-quality dependence is not yet.
- **Neither dataset reaches the originally-hypothesized ">0.8 cosine similarity for a majority of
  samples" bar beyond n~2-4.** CIFAR-100 anisotropy ratio: 86.4. CUB-200: 34.0 (both far above an
  isotropic baseline's ~1.0, confirming real ViT features are indeed strongly anisotropic as
  predicted — but that anisotropy is not, on its own, enough to push reference-based (as opposed to
  oracle) reconstruction fidelity above the 0.8 bar at realistic per-class n).

## What this means for H5

The **original** hypothesis ("cosine similarity > 0.8 for a majority of samples... at n <= 64") is
**not supported as literally stated** — the >0.8 bar is met only near n=1-2, well below 64. But the
**re-specified** hypothesis (`agents/OPEN_QUESTIONS.md`: "an n-threshold curve as a function of
reference quality and feature anisotropy... the curve is the deliverable regardless of where it
lands") **is fully answered, honestly, with real data**: there is a real, substantial,
non-chance-level reconstruction signal (cosine 0.4-0.7, not ~0) that persists out to the largest n
tested, it is stronger for the more fine-grained dataset as predicted, and it is far short of the
originally-hoped-for near-perfect reconstruction at moderate n. This is a **defensible, nuanced
finding, not a failure** — it says F5 (the family the FCL literature treats as safest) leaks a real,
measurable amount at every practical n, just not at the "your name is legible in the reconstructed
photo" fidelity the original threshold implied.

Updated `agents/OPEN_QUESTIONS.md`: H5 -> `SUPPORTED` (re-specified curve; original numeric threshold
not met), with the exact numbers and this file cited.

## What the next person needs to know

- 5 trials/cell is thin for the reference-quality axis specifically (the n-dependence is robust with
  this many trials; the noise/pool-size dependence is not). If this curve is going into the paper as
  FIG13, increase `N_TRIALS_PER_N` in `run_gram_inversion.py` (e.g., to 20-30) and re-run — it's cheap
  (CPU-only, the full 195-row run took well under the 2-hour walltime budget) — before trusting the
  reference-quality comparison specifically.
- No qualitative reconstruction montage (the "decoded-image montage for the CUB case" `03_RESULTS_SPEC.md`
  mentions as an optional qualitative panel) has been produced — would need an image-space decoder
  (feature inversion network) trained on public data, which is separate, unbuilt work.
- `run_gram_inversion.py` currently only exercises the primary backbone; a DINOv2 repeat would be a
  natural robustness check given DINOv2's features are cached for all 4 datasets already.
