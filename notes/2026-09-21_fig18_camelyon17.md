# 2026-09-21 — FIG18: Camelyon17 natural federation, the last "never cut" item

## Scope decision

The human asked directly: "what other do-not-cut item are we missing?" After completing FIG11
(secure agg), FIG16 (log-log ROC), FIG17 (seed variance), and `make verify`/`make paper`, the answer
was the Camelyon17 natural-federation check (FIG18) — previously flagged as out of scope given the
deadline, since it needs a whole new dataset. The human said "ok start FIG18" — this note documents
what was actually built, at what scope, and the real data-acquisition problem it ran into.

## The blocker: the official download does not work from this cluster

`p3fcl.get_data.fetch_camelyon17()` calls `wilds.get_dataset(dataset="camelyon17", download=True,
root_dir=...)`, which is hardcoded (in the `wilds` package itself) to fetch from
`https://worksheets.codalab.org/rest/bundles/0xe45e15f39fb54e9d9e919556af67aabe/contents/blob/`.
**This host times out on every connection attempt from the Kodiak login node** — checked directly
with `curl -v`: DNS resolves fine (`20.232.203.197`), but the TCP handshake on port 443 times out
after 10s, consistently, on repeated attempts. General internet access is fine (`pypi.org`,
`huggingface.co`, `google.com` all respond normally in under a second) — this is specific to that one
host, either a remote-side outage/rate-limit at CodaLab (a known-fragile research-data host) or a
network path issue specific to that IP range. Either way, it is an external blocker this session
cannot fix by writing code.

## The workaround: a verified community mirror, same public-domain data

`wltjr1007/Camelyon17-WILDS` on Hugging Face Hub (reachable, unlike CodaLab) is a community
re-hosting of the same dataset — verified directly, not assumed: downloaded one shard first and
confirmed identical schema (`image.bytes`, `label`, `center` 0–4, `patient`, `node`, `slide`,
`x_coord`, `y_coord`) and matching per-center row structure to the official WILDS release. Camelyon17
is CC0 public domain (stated in the `wilds` package's own `camelyon17_dataset.py` docstring), so a
faithful re-hosting carries the same license — this is not a new ethics question beyond what
`RESEARCH_PLAN.md §9` already covers for this dataset.

Downloaded all 21 parquet shards (14 train + 3 validation + 4 test, ~20GB total — `pyarrow` had to be
installed, it wasn't already in the venv). Confirmed all 5 hospitals (centers 0–4) are present once
all three original splits are pooled (the official WILDS split scheme reserves center 1 for its own
"OOD validation" and center 2 for "OOD test," so a single split alone does not cover all 5 hospitals —
pooling train+validation+test does).

**Reconstructed the on-disk layout `wilds.datasets.camelyon17_dataset.Camelyon17Dataset` expects**
(`<root>/camelyon17_v1.0/metadata.csv` + `patches/patient_<p>_node_<n>/patch_..._x_<x>_y_<y>.png`,
confirmed by reading the `wilds` package's own source) via a new script,
`code/scripts/build_camelyon17_from_hf_mirror.py`. Two-phase, to avoid materializing all 455,954
images: (1) write the full `metadata.csv` from just the cheap non-image columns of every shard, (2)
after `prepare_camelyon17()` runs its existing class+hospital-stratified subsampling logic over that
full metadata (no images needed for this step), materialize PNG files only for the specific
`wilds_index` values actually selected. **Verified end to end**: `wilds.get_dataset(download=False,
root_dir=...)` loads the reconstructed metadata correctly (455,954 samples, all 5 hospitals present,
labels exactly balanced 227,977/227,977 — matches the known dataset design), and `ds[i]` correctly
reads back a materialized image with the right label and hospital metadata.

**This required no changes to `p3fcl.get_data.prepare_camelyon17()` at all** — it was already written
correctly and generically against the `wilds` Dataset object API; only the *data underneath* it needed
reconstructing, not the code that consumes it.

## Scope of this pilot

- **Subsample**: `subsample_target=5000` (well below `02_DATASETS.md`'s own ~60k target for
  shadow-scale sweeps, itself already a deliberate reduction from the full 455,954) — 4,998 selected,
  class+hospital-stratified, split 3,998 train / 500 test / 500 ref.
- **Method**: M0 only. The question FIG18 asks — does the client-partition scheme change the
  decoupling finding — is testable with one method; extending to more is a real follow-up, not
  claimed here.
- **Stream**: domain-incremental (one task per hospital, 5 tasks total) — Camelyon17 is binary-label
  (tumor/normal), so the class-incremental split every other dataset in this project uses (which
  needs multiple disjoint class groups per task) is not applicable. `streams.build_stream` already
  supported `domain_field` for exactly this case (built in an earlier phase, never previously
  exercised against real data) — no new stream-partitioning logic was needed.
- **Two client-partition arms, both via the same already-generic `build_stream`, zero new
  partitioning code**: **natural** (`n_clients=1` — the hospital itself is the sole client for its
  task, no Dirichlet anywhere) and **dirichlet** (`n_clients=10`, matching every other dataset's
  client count). `shadow_runner.py` gained one new config flag, `stream.use_domain_field`, to switch
  from the default class-incremental path to the domain-incremental one (threaded the same way as
  `method_config_override`/`adversary_view` — additive, default-off, no change to the other 3
  datasets' behavior).
- **3 seeds, reduced 1,024-shadow budget** — pilot scale, matching every other post-deadline addition
  this session.

## Real result

`results/accuracy_matrix_camelyon17.csv` (real, non-shadow federations) and
`results/fig18_natural_federation.csv` (calibrated A1 TPR@1%FPR from the shadow stores), merged and
plotted in `figs/fig18_natural_federation.pdf`:

- **Accuracy**: natural federation shows mild forgetting (BWT ≈ −0.02, consistent across all 3 seeds
  — with `n_clients=1` there is no Dirichlet randomness, so seed-to-seed variance collapses to
  whatever the training procedure's own residual randomness contributes, which turned out to be
  none here); Dirichlet-subpartitioned shows *positive* backward transfer instead (BWT ranging
  +0.001 to +0.030 across seeds).
- **Leakage**: **the natural federation shows a real, rising TPR@1%FPR trend (~0.025 at elapsed=0 to
  ~0.055 at elapsed=4, pooled across seeds), while the Dirichlet arm stays comparatively flat
  (~0.012–0.018 across the same range).** The natural arm's CI is wide at high elapsed (one seed's
  TPR reached 0.118 at elapsed=4, pulling the band up) — a real consequence of only 3 seeds at pilot
  scale, stated honestly, not hidden.

**The headline sentence this supports, and it is the opposite of what the "your clients are a
Dirichlet artifact" objection would predict**: under Camelyon17's real hospital structure, leakage is
*higher* and more clearly increasing than under a synthetic Dirichlet split of the same data — if
anything, the synthetic partitions used everywhere else in this project *understate* real-world risk
for this kind of federation, not overstate it. This is a stronger, more useful answer to the
objection than "no difference" would have been.

**Honest caveats**: M0 only (not the full 7-method zoo); 3 seeds, wide CIs at the high-elapsed end;
~5,000-image subsample of the full 455,954-patch release (both arms use the identical subsample, so
the comparison itself is apples-to-apples even though absolute numbers would shift with a larger
sample); the plausible mechanistic story (fewer, larger real clients release more concentrated,
more attributable signal per update than many small synthetic clients) is offered as a hypothesis,
not independently verified further this session.
