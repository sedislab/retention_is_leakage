## Surprises

- **Path mistake caught and fixed at the start of the session**: `build/00_BUILD_PLAN.md` and
  `build/01_KODIAK.md` still had leftover `/data/$USER/p3fcl/...` filesystem paths (features/, raw/,
  shadows/, envs/, hf/, torch/) from an earlier draft where the repo lived at a different path.
  Corrected to `/data/$USER/retention_leakage/...`, matching `CLAUDE.md`'s layout diagram (repo root
  IS the data root — no separate sibling tree). Left `code/src/p3fcl/` and `python -m p3fcl.cli`
  alone since those are the package name / module invocation, not filesystem paths.
- **The venv's python needs `python/3.10.4` loaded in *every* shell that uses it**, not just the one
  that built it — it dynamically links `libpython3.10.so.1.0`, which only resolves via the module's
  `LD_LIBRARY_PATH`. Bit the first `make test` run from a fresh shell. Fixed by baking
  `module load python/3.10.4` into `code/Makefile`'s `$(ACTIVATE)` and into every `.pbs` template;
  worth remembering for any future ad-hoc shell.
- The general `gpu` queue was fully occupied (10/10 GPUs running other users' jobs) at submission
  time — expected given Kodiak's small GPU pool (`01_KODIAK.md §5`: "ten GPUs is a shared resource
  among the whole university"), but it means P0's gate item "one job successfully submitted and
  returned" may take a while to actually *return*, independent of anything in this codebase.

## What the next person needs to know

- Everything in this note plus current job state is mirrored in `build/STATE.md` — read that first
  if resuming cold.
- `dp.mechanisms` ships **binary-tree aggregation** (`tree_aggregation_factor`), not the SOTA banded
  matrix-factorisation mechanism from Choquette-Choo et al. — that upgrade is explicitly P7's job
  per `build/00_BUILD_PLAN.md`. Binary-tree aggregation is a real, fully-specified mechanism with an
  honest polylog(T) cost, not a placeholder any reported number depends on.
- `methods/m4_proto.py`'s momentum-based `touched` propagation is worth a second look before it's
  relied on for a real result: under class-incremental streams a class never recurs across tasks, so
  momentum carry-over never actually fires and the method stays task-disjoint (matches H6). Under
  domain-incremental streams (Camelyon17) the same classes recur every task, momentum > 0 genuinely
  carries old influence forward, and `check_disjointness` correctly flags V2/V3. Both directions are
  covered by `tests/test_methods.py`.
