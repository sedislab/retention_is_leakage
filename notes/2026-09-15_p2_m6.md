# 2026-09-15 — P2: M6 (C²Prompt) built, one real bug caught pre-GPU, validated on real hardware

## What happened

Built `methods/m6_prompt.py`: a prompt pool spliced into a frozen timm ViT's forward pass (after
CLS, no positional embedding of its own — the pretrained pos-embed is applied only to [CLS, patch
tokens] before prompts are inserted, so the backbone's pretrained positional structure for the tokens
it actually saw in pretraining is untouched). Only the prompt pool, prompt keys, and classifier head
are trainable; the backbone stays frozen throughout.

**Caught a real bug before spending any GPU time**, by testing the mechanics on CPU with a tiny
untrained `vit_tiny_patch16_224` first: `pool_keys` never updated during training.
`sim.topk(k, dim=-1)` returns both `.values` (differentiable) and `.indices` (not, by construction —
which entries get picked can't have a gradient), and the first version of this file used only
`.indices`, silently discarding the only gradient path into `pool_keys`. This is exactly why the real
L2P/DualPrompt line of methods includes an explicit key-query cosine-alignment loss term rather than
relying on backprop through the selection itself — I'd omitted it, not realizing the selection step
was the reason. Fixed by adding `key_loss = -topk_sim.mean()` to the training objective. Re-verified
on CPU that prompts, keys, and head all update correctly and the backbone never receives a gradient.

Then ran a real, small validation job on the actual GPU queue (`vit_base_patch16_224.augreg_in21k`,
real CIFAR-100 images, 2 tasks x 2 clients, 20 images/class subsample, 1 local epoch — deliberately
cheap, meant to prove convergence, not produce a headline number):

```
task 0: acc on task 0 = 0.641
task 1: acc on task 0 = 0.054, acc on task 1 = 0.639
final_avg_acc = 0.3465, bwt = -0.587
```

This is a completely sensible result: real above-chance learning each task (chance = 1/50 for a
2-task, 50-class-each split of CIFAR-100), and real, substantial catastrophic forgetting once task 1
is learned (0.641 -> 0.054) — expected, since this configuration gives the prompt pool no explicit
mechanism to protect old-task performance beyond whatever the shared pool structure does naturally,
and 1 local epoch on 20 images/class is a genuinely small training budget. The magnitude and
direction of every number is exactly what the mechanism as implemented should produce; nothing here
looks like an artifact of a bug.

## What was deliberately NOT done, and why

- **No full TAB05-shape sweep for M6** (4 datasets x multiple n_tasks x 3 seeds). This validation run
  used a heavily subsampled dataset and a single seed specifically to keep the first real-hardware
  attempt cheap, given how contested the `gpu` queue has been all session (the torch probe alone
  queued 7+ hours earlier the same day). A full sweep is a materially larger GPU-hour commitment and
  a separate scope decision from "does the mechanism work at all."
- **M7 (TPGP) not started.** Lowest priority per `00_BUILD_PLAN.md`'s own stated cut order ("keep M6
  C²Prompt — it is the current SOTA and the more-cited family" when something has to be cut), and M6
  alone already demonstrates the project can build and validate a real backprop-through-the-ViT
  method when it needs to — the remaining question for M7 is purely "is it worth the additional
  engineering and GPU-hour cost," which is a scope call, not a technical blocker.

## What the next person needs to know

- `methods/m6_prompt.py` and `scripts/run_prompt_method.py` are real and tested, but the driver is
  intentionally separate from `sim.run` (which assumes cached feature arrays) — any later work
  extending M6/M7 into the shadow-federation runner (P3) will need its own image-loading path too,
  not `sim.run`'s.
- The `key_loss_weight` hyperparameter (default 0.5) hasn't been tuned at all — the validation run's
  job was to prove the mechanism trains, not to find a good operating point.
- If a full sweep is authorized later, budget real GPU-hours for it up front and expect to serialize
  it the same way P1's extraction jobs were serialized (one at a time on the `gpu` queue).
