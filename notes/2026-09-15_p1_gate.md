# 2026-09-15 — P1 gate: all 4 datasets × both backbones extracted and sanity-checked

## What happened

Ran the full P1 pipeline for real, on Kodiak, end to end: fetch (batch job) -> prepare (batch job,
builds `datasets/<name>/index.json` + our own train/test/ref/canary splits) -> audit -> extract
(GPU job, `features.extract()`) -> sanity check (linear probe). All 4 required datasets (CIFAR-100,
ImageNet-R, CUB-200-2011, Camelyon17-WILDS) × both backbones (`vit_base_patch16_224.augreg_in21k`
primary, `vit_base_patch14_dinov2.lvd142m` robustness) are extracted, cached, and sanity-checked.
Every fetch/prepare/extract ran as a real PBS job — nothing ran in-process on the login node.

**Zero debugging needed across all 8 (dataset x backbone) extraction runs and all 4 prepare runs**,
including the two code paths that had never executed before this session: the `wilds:camelyon17`
loader branch in `features.extract()` (loads via `ds.get_input(idx)` instead of `PIL.Image.open`),
and the DINOv2 backbone path (different patch size/config, resolved generically via
`timm.data.resolve_data_config` rather than any hardcoded assumption). That is a stronger result than
"it worked" — it means the genericity built into `get_data.py`'s index format and `features.extract()`'s
loader abstraction actually paid off, rather than needing dataset-specific special-casing after all.

## A real provenance gap, found and fixed but not fully backfilled — read this before trusting GPU-hour numbers

`cli.py`'s `_cmd_extract` never called into `provenance.run_manifest`/`finalize` — none of these 8
extraction runs were captured in `results/RUN_LOG.jsonl`, which is a direct miss against CLAUDE.md
non-negotiable #10 ("a run not in the log did not happen") and the P1 gate's "total GPU hours recorded
in the run log" criterion. Fixed the code (`_cmd_extract` now wraps every call in a real manifest +
`finalize`, so every future extraction is logged) but **did not fabricate retroactive RUN_LOG.jsonl
entries for the 8 runs that already happened** — inventing a `source_hash`/`config_hash` for a run
after the fact, when neither was actually captured live, would be dishonest bookkeeping dressed up as
provenance. What *does* honestly exist as evidence these runs happened correctly:
- The feature cache files themselves (`features/*.npz` + `*.json` sidecars) with correct
  dataset/backbone/split/n/d metadata, referenced by content in `tab01_feature_sanity.csv`.
- `tab01_feature_sanity.csv`'s own rows *are* properly provenance-stamped (`sanity_check_features.py`
  already used `provenance.run_manifest`/`finalize` correctly from the start) — the sanity numbers
  above are real logged results, just the upstream extraction step that produced their inputs wasn't.
- PBS job ids for all 8 runs (135268, 135280, 135283, 135285, 135291, 135317, 135345, 135346) and
  approximate wall-clock timing reconstructed from `.OU` log file mtimes (PBS's own job-history
  retention is only 30 minutes, so `qstat`-based accounting had already expired for 7 of the 8 by the
  time I went to total it — only 135346's `resources_used.walltime` (00:52:24) was still queryable).

**Best-effort total GPU-node-time across all 8 jobs, from `.OU` mtime deltas: ~2.9 hours.** This
conflates queue-wait with active compute (Kodiak's `gpu` queue was contended most of the day) and is
therefore an over-estimate of actual device-active time, not an under-estimate — treat it as "total
resource commitment," not "GPU-hours billed." If a precise number is ever needed for a paper's
reproducibility appendix, it will have to come from future runs now that logging is fixed, not these.

## What the next person needs to know

- The provenance-logging gap above is now closed going forward — any new `p3fcl.cli extract` run
  writes a real `RUN_LOG.jsonl` line with `source_hash`, `config_hash`, `pbs_jobid`, `wall_seconds`.
- If a similarly "obviously should be logged" CLI path is added later (shadows, attack, account,
  audit, sweep), check it actually calls `provenance.run_manifest`/`finalize` before trusting its
  entry in `RUN_LOG.jsonl` — this is now the second time in the session an under-instrumented path
  was found only by manually checking (`get_data.py`'s fetch/prepare and `sanity_check_features.py`
  both got it right from the start; only `extract` was missed, because it was written slightly
  earlier and the pattern hadn't been established yet).
