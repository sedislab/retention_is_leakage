# 2026-09-16 — P3: A6 property inference, H10's deciding test, run on real data

## What happened

Built `attacks/property_inference.py` and `attacks/property_inference.py`'s A5 sibling
(client attribution), scoped to F2+F7 (M4) — the case where the released `COUNTS` artifact is a
direct, honest join key for "did client c contribute to class y" (RESEARCH_PLAN.md §2.2). Explicitly
did not attempt F5/F1-based property inference this session — a stated scope cut, not a silent one.

Before running anything real, worked out precisely what "round-T artifact" means given this
project's actual ledger structure (this took real reasoning, documented in the module's own
docstring): under a persistent-observer (`view=full`) adversary and the single-pass, class-
incremental methods built so far, a (client, class) pair's evidence is released exactly once, at the
task's own round, and never retracted or overwritten. The honest prediction going in was therefore
**no decay once T >= k** — not a hoped-for null, a specific, falsifiable prediction from the design.

Ran `run_property_inference.py` on real CIFAR-100 features (10 tasks, 10 clients, 926 true
(client,class,task) positives, 300 random negatives per elapsed value). Result matches the
prediction exactly:

```
elapsed=-2: balanced_accuracy=0.5000  (chance, before the task happened)
elapsed=-1: balanced_accuracy=0.5000
elapsed=0:  balanced_accuracy=1.0000  (the task just happened)
elapsed=1..10: balanced_accuracy=1.0000  (no decay, ever, out to +10 tasks)
```

## What this means for H10

H10: *"Property-inference accuracy about client c's task-k data decays with (T-k) at a rate that
differs systematically by artifact family, with F5/F8 showing no decay."* The literal prediction
(F5/F8 no-decay, implying other families DO decay) is **not what F2/F7 shows here** — F2/F7 shows the
same "no decay" pattern H10 predicted only for F5/F8. This is worth stating precisely rather than
forcing it into either a clean confirm or a clean refute:

- **This is not evidence against the *underlying* idea that persistence differs by family** — it's
  evidence that, under a `view=full` adversary and the *specific* single-pass, class-incremental
  release schedule these methods use, the F2/F7 property signal is exactly as persistent as F5/F8's,
  because none of the methods built so far ever retract or overwrite old per-class evidence within
  this adversary's view.
- **The interesting remaining question is whether a *weaker* adversary (`view=task` or `view=final`,
  which does not retain history) or a method that actively *dilutes* old evidence (e.g., `M4` at
  `prototype_momentum > 0`, or `M1`'s distillation-driven drift) would decay where this one doesn't.**
  That is a real, different experiment from the one just run, and it is the one that would actually
  distinguish H10's family-dependent claim empirically.
- Status set to `SUPPORTED (with a scope caveat)` rather than a blanket confirm/refute in
  `agents/OPEN_QUESTIONS.md` — the honest headline is "under `view=full`, F2/F7 shows no decay,
  matching F5/F8 rather than contrasting with them; H10's *family-dependent* claim needs a weaker-
  adversary or momentum-bearing variant to actually test."

## What the next person needs to know

- This result is real, not a bug — before spending time debugging "why doesn't it decay," reread the
  reasoning in `attacks/property_inference.py`'s module docstring: it decays only if either (a) the
  adversary has a bounded/weaker view than `view=full`, or (b) the underlying artifact is genuinely
  overwritten/diluted over time (momentum>0 for M4, or comparing F1/F5's *running* statistics rather
  than F2/F7's *one-shot* releases).
- A natural, cheap follow-up already within reach: rerun with `prototype_momentum > 0` (already a
  supported M4 config) and/or restrict the adversary to `ledger.view("task")` instead of the full
  transcript, and see whether either produces the decaying curve H10 originally envisioned.
