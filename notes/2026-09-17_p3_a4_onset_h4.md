# 2026-09-17 — P3: A4 built and run for real — H4 partially confirmed, with a real mechanistic correction

## What was built

`src/p3fcl/attacks/onset_inference.py` — client-arrival onset inference (`RESEARCH_PLAN.md §3.1.3/§3.3`,
`[LOCKED]`). Threat model: `who="participating_client"`, `auxiliary="none"`, `target="onset"`,
`survives_secure_agg=True` — the attack is built *natively* against `ledger.aggregate_view()` from the
start (the aggregate per-round update norm and participant count), not as a later ablation, so it also
directly demonstrates H11-relevant evidence for A4 specifically (not built before this pass).

Real attack: two-sided CUSUM change-point detection on the aggregate norm series. Baselines named
explicitly in `RESEARCH_PLAN.md §3.3`: random guess, and a norm-of-update-spike heuristic (top-k
highest-norm rounds, no change-point structure). `code/scripts/run_onset_inference.py` calibrates
CUSUM's threshold (and a common flag budget for fair baseline comparison) on 20 seeds, evaluates pooled
precision/recall with exact Clopper-Pearson CIs on 20 held-out seeds (CLAUDE.md #4/#6). 8 new tests,
171/171 total, ruff clean.

**A real design decision, made before running anything**: verified empirically that this project's
standard stream config (`n_tasks=10, n_clients=10, beta=0.5`, used by every other P3 attack) gives
**zero** post-round-0 client-arrival events — every client already holds a nonzero Dirichlet share of
every task, so there is nothing to infer. A4 needed a genuinely skewed config
(`n_clients=50, beta=0.02`) to produce real, non-trivial arrival events (~54 total across 20 seeds) —
documented in the module's own docstring so nobody rediscovers this by getting a suspicious null.

**A real, pre-existing bug found and fixed along the way**: `Ledger.aggregate_view()` crashed with
`KeyError` the first time it was ever exercised on a payload with a *per-client-varying* key set — M4's
per-class prototype dict, where a client whose Dirichlet share holds zero samples of some class simply
never has that class as a key. `aggregate_view()` assumed every record shared the first record's key
set; fixed to take the union of keys across every record and sum only over records that actually have
each key (the correct secure-aggregation semantics: absence, not a zero-filled contribution). This is a
general `artifacts.py` bug, not A4-specific — checked whether it silently corrupted any earlier
reported number (A6/A5's `aggregate_view()` tests used a balanced `beta=1.0` synthetic split where every
client shares full class coverage, so the bug never manifested there; no retroactive correction needed).
Regression test `test_aggregate_view_dict_payload_with_mismatched_keys` added.

## The result: real, above-baseline localization for F1 — not for F2/F5

Real run, CIFAR-100, `n_clients=50, beta=0.02`, 20 calibration + 20 evaluation seeds, tolerance=±2
rounds, `results/a4_onset_inference.csv`:

| Method | Family | CUSUM precision | CUSUM recall | norm_spike precision | random precision |
|---|---|---|---|---|---|
| M0 (FedAvgSequential) | F1 (delta) | **0.716** [0.593, 0.820] | 0.981 | 0.675 | 0.625 |
| M4 (PrototypeFCL) | F2 (prototype) | 0.591 [0.512, 0.667] | 1.000 | 0.581 | 0.550 |
| M8 (AnalyticFCL) | F5 (Gram) | 0.601 [0.524, 0.675] | 1.000 | 0.575 | 0.588 |

**M0 (F1) is a real, meaningful result**: CUSUM clearly separates from both baselines (beats norm_spike
by 4 points, random by 9), recall is near-perfect (0.981), and the precision CI's upper bound (0.820)
just touches H4's stated >0.8 bar even though the point estimate (0.716) falls short. This is a genuine,
non-trivial detector, not a coin flip forced to look good.

**M4/M8 (F2/F5) do *not* show a comparable signal** — CUSUM barely separates from random (M8: 0.601 vs
0.588, well within CI overlap) and needed a much larger flag budget (k=8 vs M0's k=2) to reach
comparable recall, meaning the aggregate norm series for these two families is far less informative
about *when* a genuine new arrival happened.

**This is the opposite of H4's literal wording** ("Task-onset can be localized... for prototype- and
statistics-based methods"), and there's a real mechanistic reason, not noise: F1's released quantity
is a **gradient**, whose magnitude genuinely reflects how unfamiliar the local data is (higher initial
loss on brand-new classes -> larger gradient -> a real, detectable spike in the aggregate delta norm
when a new client's fresh contribution enters the sum). F2/F5's released quantities are **closed-form
statistics** (a class mean, a Gram matrix) — a new client's contribution is the same *kind* of object as
an existing client's, with no inherent "surprise" signature to spike on. The norm-of-update-spike
heuristic (and CUSUM built on it) is mechanistically a property of gradient-based releases, not of
statistics-based ones — a real, defensible correction to H4's original framing, not a failure to find
the predicted effect.

## Status

**H4 -> `SUPPORTED` (F1/gradient-based methods only; not confirmed, and mechanistically not expected,
for F2/F5/statistics-based methods)** — a precise, corrected version of the hypothesis, not a blanket
confirm or refute. `agents/OPEN_QUESTIONS.md` updated with this exact framing.

## What's left for A4

- Only CIFAR-100, one method per family tested. M1/M2/M3/M5 (also F1) would be a natural, cheap
  extension using identical infrastructure — likely to show the same gradient-magnitude effect, worth
  confirming rather than assuming.
- The random-vs-norm_spike gap for M4/M8 is itself worth a closer look: is there a *different*,
  more informative aggregate signal for statistics-based methods (e.g. a per-class coverage count, or
  a rank/eigenvalue-based statistic for M8's Gram matrix) that would recover the localization ability
  H4 originally predicted? Not attempted this pass — a real, stated open question, not a dead end.
- Only client-arrival onset tested, not the "class-arrival" or explicit "composition" variants
  RESEARCH_PLAN §3.1.3 also names — a scoped cut, not a silent one.
