# CLAUDE.md — P3 / "Retention Is Leakage"

Standing rules for **every** Claude Code session in this repository. Read this first, then
`build/00_BUILD_PLAN.md`, which says what to build and in what order.

---

## What this repo is

**You are building `code/` from scratch.** There is no prior implementation to reuse or port; the
abstractions are specified in `build/06_PACKAGE_SPEC.md` and that file is the source of truth for
them. Do not go looking for an existing skeleton.

The experimental system behind one paper:

> **Retention Is Leakage: A Stability–Plasticity–Privacy Trilemma in Federated Continual Learning**
> Target: ICLR. Thesis: in federated continual learning the mechanism that prevents forgetting is
> the mechanism that prevents privacy from decaying, so the centralized result that forgetting
> passively amplifies privacy (Jagielski et al., ICLR 2023) **inverts** once the adversary sees the
> whole broadcast transcript instead of a final model.

Four claims the code must produce evidence for:

| ID | Claim | Primary artifacts |
|---|---|---|
| **C1** | Leakage half-life differs by artifact family and decouples from accuracy decay | FIG01, FIG02, FIG06, TAB03, TAB04 |
| **C2** | Within a method, retention strength causally drives leakage (dose–response) | FIG03, FIG04, TAB06 |
| **C3** | Contractive retention admits a T-independent lifelong ε; accumulating retention does not | FIG05, TAB02, TAB10 |
| **C4** | A bounded-influence retention operator keeps ε flat in T at competitive accuracy | FIG08, FIG09, TAB08 |

Hypothesis IDs (H1–H12, T1-fwd, T1-conv, T2) live in `agents/OPEN_QUESTIONS.md`. **That file is
the project's state.** Every experiment you run must name the hypothesis it tests, and you must
update its status line when a deciding test completes. Only the human sets `CONFIRMED`.

## How you work: the autonomy contract

**Run autonomously. Do not ask for permission phase-by-step.** Inside a phase you decide, implement,
submit, poll, debug, and move on without checking in. You have standing authority to: create and edit
any file in this repo; install packages into the project venv; download the datasets named in
`build/02_DATASETS.md`; submit, monitor and delete **your own** PBS jobs; and write results.

**Stop and ask the human in exactly four situations, and no others:**

1. **A phase gate passes.** Report what was built, what the gate showed, the key numbers, and ask:
   *"Proceed to Pn+1?"* Then wait. This is the only routine checkpoint.
2. **A gate fails twice for the same reason.** Do not try a third variant. Write the problem into
   `notes/` with the date and bring it up.
3. **Something would relitigate a `[LOCKED]` decision** in `RESEARCH_PLAN.md`, or contradicts
   `agents/OPEN_QUESTIONS.md`. Log the evidence there and stop.
4. **A hypothesis needs its status set to `CONFIRMED`.** Only the human does that. You may set
   `SUPPORTED` or `REFUTED` yourself.

Everything else — a failing test, a missing package, a job that died, a design choice inside a
phase, a figure that looks wrong — you handle. Fix it and keep going.

**Never idle.** If a job is queued or running, switch to the next task that does not depend on it.
There is always CPU-side or code-side work available; `build/00_BUILD_PLAN.md` says which phases
overlap. Polling a queue in a loop while doing nothing else is wasted wall-clock.

**Keep `build/STATE.md` current.** Update it after every meaningful step: the phase, the task, what
just finished, what is queued with its job id, what is next, and anything a fresh session would need.
Your context will be compacted or reset during a run this long. `STATE.md` plus
`results/RUN_LOG.jsonl` is how the next session picks up without redoing work. A run not in the log
did not happen.

**You are on the Kodiak login node.** Editing and `qsub` only — never train, extract or sweep
in-process. This is Kodiak policy, not a preference, and it is the instruction most likely to erode
over a long session. Re-read it when you catch yourself about to run something heavy.

## Non-negotiables

1. **The ledger is the only interface.** Methods declare what they *release* as `ArtifactRecord`s
   (`src/p3fcl/artifacts.py`). Attacks and the accountant consume the ledger and nothing else.
   Never reach into a method's internal state from an attack. Nine methods with nine checkpoint
   formats is how this project dies; one ledger is how it ships.

2. **`touched` is privacy-critical.** A datum touched only through a replay buffer, a distillation
   term or a regulariser still counts. Under-reporting `touched` silently converts a false privacy
   claim into a "proved" one. If you are unsure, over-report and note it.

3. **No number reaches the paper except through a CSV.** Every figure and table is generated by a
   script that reads a committed CSV under `results/`. Plot scripts never recompute. `make verify`
   must pass: it greps the LaTeX for numeric literals that cannot be traced to a results file.
   Do not hand-type a result into prose, a caption, or an abstract. Ever.

4. **Seeds and intervals.** ≥3 seeds for anything reported, ≥5 for headline numbers. Report
   mean ± 95% CI. Rates (TPR, precision, accuracy on finite test sets) get Clopper–Pearson exact
   intervals — `metrics.clopper_pearson` already exists, use it.

5. **Membership results are never reported as AUC alone.** TPR@1%FPR and TPR@0.1%FPR are primary;
   log-log ROC is mandatory in the appendix. This is the Carlini et al. (2022) standard and
   reviewers at this venue enforce it.

6. **Never tune on the evaluation split.** Attack hyperparameters are selected on a held-out
   *shadow* split. Record the selection procedure in the run manifest.

7. **Negative results are results.** If an attack is weak, report it with an audited ε lower bound
   (`audit/one_run.py`) rather than quietly dropping it. If a hypothesis is refuted, mark it
   `REFUTED` in `agents/OPEN_QUESTIONS.md` and keep the evidence. Do not delete failed branches.

8. **Do not chase original codebases.** Reimplement published methods faithfully inside our harness
   against the paper's description, verify against the published number within a stated tolerance,
   and report the gap. Reproduction attrition is hypothesis H12 — a *finding*, not a failure.
   Time-box any single reproduction attempt to one working session.

9. **`[LOCKED]` decisions in `RESEARCH_PLAN.md` are not yours to relitigate.** If evidence
   contradicts one, write the evidence into `agents/OPEN_QUESTIONS.md` and stop for a human.

10. **Log everything.** Every run appends one line to `results/RUN_LOG.jsonl`: **source hash**,
    config hash, seed, host, PBS job id, wall time, exit status, output paths. A run that is not in
    the log did not happen. There is **no git in this project** — the source hash is a SHA-256 over
    the sorted contents of `code/src/**/*.py` and `code/configs/**`, computed by
    `provenance.source_hash()`. It does the same job: it tells you exactly which code produced a
    number, and it changes when the code changes.

11. **No credentials in the repo, ever.** No passwords, no tokens, no `.env`, not in a job script and
    not in a comment. Cluster access is by SSH key. If one lands in a commit, rotate it and rewrite
    history rather than deleting it in a later commit.

12. **Kodiak forbids data classified Protected or higher.** Every dataset in this project is a public
    research release, which satisfies the policy by design — but never stage clinical, identifiable
    or otherwise protected data onto the cluster, not even to test a pipeline. See
    `build/01_KODIAK.md §0`.

## Compute reality (read before designing any experiment)

Experiments run on **Baylor Kodiak** (`build/01_KODIAK.md`). Kodiak is **PBS/Torque** (`qsub`), not
Slurm, and has roughly **ten GPUs cluster-wide** (2 nodes × dual P100 16GB, 3 nodes × dual V100
32GB) against many 36-core CPU nodes. There is no wall-clock budget, but GPU concurrency is the
binding constraint.

The design consequence is not optional, it is the architecture:

- **GPU is used for exactly two things:** (a) one-time frozen-backbone feature extraction per
  dataset × backbone, and (b) the two methods that require backprop through the ViT (prompt pool,
  LoRA). Nothing else may request a GPU.
- **Array geometry is fixed by a hard cap:** `batch` allows one user 512 concurrently running
  cores. Shadow arrays run `-l select=1:ncpus=8`, `-J 0-N%60` (= 480 cores, headroom for a GPU job).
  See `build/01_KODIAK.md §2`.
- **Everything else is linear algebra on cached features and runs on CPU array jobs.** The shadow
  federations for LiRA — thousands of them — are CPU work. This is what makes an audit of this
  size affordable on this cluster. The GPU methods are **M6, M7 and M4's LoRA half**; everything
  else stays on CPU.
- Any design that needs a GPU per shadow model is wrong. Redesign it.

## Layout

```
build/          the instructions you are following (00–06). Start at 00.
                STATE.md is yours to maintain — it is how a fresh session resumes.
code/           the package YOU build, to build/06_PACKAGE_SPEC.md.
  src/p3fcl/    artifacts, streams, sim, metrics, features, methods/, attacks/, dp/, audit/

  scripts/      job scripts and CLI entry points
analysis/       one script per figure/table. Reads CSV, writes PDF/TeX. No computation.
results/        CSVs + meta.json + RUN_LOG.jsonl. The paper's evidence base.
figs/           generated PDFs/PNGs. Never edited by hand.
tables/         generated .csv and .tex. Never edited by hand.
paper/          LaTeX. Already scaffolded in llm/paper/.
agents/         the multi-agent debate scaffolding. OPEN_QUESTIONS.md is the state file.
notes/          working notes. Toy-scale observations are labelled NOT EVIDENCE.
```

## Commands

```bash
make setup        # env + editable install + dataset manifest check
make test         # pytest; four of these are CLAIM tests, treat failures as broken arguments
make smoke        # end-to-end on synthetic features, no downloads, < 60s
make figures      # regenerate every figure and table from results/*.csv
make verify       # provenance check: every number in paper/ traces to a results file
make paper        # latexmk
```

## Definition of done for any task

- Tests pass, including the claim tests.
- The deliverable CSV exists, has the schema named in `build/03_RESULTS_SPEC.md`, and has a
  sibling `.meta.json` with source hash, config hash, seeds and wall time.
- The figure/table regenerates from that CSV with `make figures` from a clean results/ directory.
- `results/RUN_LOG.jsonl` has the run.
- `agents/OPEN_QUESTIONS.md` is updated if a deciding test completed.
- Anything surprising is written to `notes/` with a date, and labelled evidence or not-evidence.
